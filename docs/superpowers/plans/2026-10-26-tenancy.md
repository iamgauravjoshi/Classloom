# Tenancy (Phase 1, Part 1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Schools register themselves, verify by email and receive a school code and primary campus, with every school's data isolated at the API, data-access and database levels.

**Architecture:**

- A `tenancy` module in the NestJS API owns tenants, campuses, users, memberships and registration tokens. Isolation comes from three layers: a request-scoped `TenantContext`, a Prisma extension that scopes every tenant-owned query, and Postgres row-level security enforced against a restricted runtime role.
- Email goes through a BullMQ queue to SMTP (Mailpit locally).
- The web app gets a public 3-step registration page and a verification page.

**Tech Stack:** NestJS 11, Prisma 7 (pg adapter), PostgreSQL 17 (RLS, `citext`), Redis + BullMQ (`bullmq`, `@nestjs/bullmq`), `@nestjs/throttler`, nodemailer, commander (CLI), Next.js 16 + next-intl, react-hook-form + `@hookform/resolvers` + Zod, shadcn/ui (Base UI), Vitest, Testcontainers (Postgres, Redis, Mailpit), Playwright + axe.

**Spec:** `docs/superpowers/specs/2026-10-26-tenancy-design.md` (read it with this plan; section numbers below refer to it).

- Branch `feat/p1-tenancy` from `main`; Conventional Commits ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`; one PR against `main`.
- New dependencies are pinned exactly (`saveExact: true`); approve or deny any pnpm build script explicitly in `pnpm-workspace.yaml` `allowBuilds`.

- Tenant-owned tables: `campuses`, `memberships`. Platform tables: `tenants`, `users`, `registration_tokens`.
- Database roles:
  - `classloom_owner` (LOGIN, BYPASSRLS, CREATEDB; owns the schema; migrations and CLI)
  - `classloom_app` (LOGIN, no BYPASSRLS; runtime `DATABASE_URL`)
  - Dev passwords equal the role names.
- Code rules (spec section 6): pattern `^[A-Z][A-Z0-9-]{1,10}[A-Z0-9]$`, no `--`, uppercase storage, reserved list exactly: `ADMIN, API, APP, WWW, MAIL, CLASSLOOM, SUPPORT, HELP, STATUS, DOCS, BLOG, STATIC, ASSETS, CDN, TEST, DEMO, ROOT, SYSTEM`.
- Limits (env defaults):

  - `REGISTRATION_TOKEN_TTL_HOURS=24`
  - `PENDING_TENANT_TTL_HOURS=48`
  - resend 3/hour per email+code
  - code availability 60/minute per IP
  - max 3 pending schools per email
- All API errors are RFC 7807 problem+json through the existing `ProblemFilter`; validation errors carry `errors[]` with `path`.
- All web copy lives in `apps/web/messages/en.json`; all email copy lives in `apps/api/messages/en.json`.
- Every new web page passes the existing E2E device projects with zero axe WCAG 2.1 AA violations in light and dark, and has no horizontal overflow at 375px.

## Review Focus

1. **Connection-pool tenant leak.** Request A sets `app.tenant_id`; a later query on the same pooled connection without a tenant must see no tenant rows (setting is transaction-local) (Task 4 test).
2. **Email-scanner prefetch.** Corporate and school mail scanners GET links before the human clicks. Rendering the verify page without JavaScript must not consume the token; only the client-side POST does (Task 11 test).
3. **Email variants.** `" Asha@School.IN "` and `"asha@school.in"` are one user. The 3-pending cap and the user upsert must treat them as the same person (Task 7 test).
4. **Non-Latin school names.** A Devanagari-only name such as `सरस्वती विद्या मंदिर` must still yield a valid suggested code, never an empty or invalid one (Task 2 test).
5. **Refresh mid-form.** Reloading on step 3 keeps steps 1–2 (draft in `sessionStorage`, cleared after a successful submit) (Task 11 test).

### Task 7: Registration, verification and resend

**Files:**

- Create: `apps/api/src/modules/tenancy/{school-registration.service.ts, school-registrations.controller.ts, mask-email.ts, mask-email.test.ts}`, `apps/api/test/tenancy/registration.int.test.ts`

**Interfaces:**

- Consumes: Tasks 3–6 (`withTenant`, `EmailService.enqueue`, `verifyRegistrationEmail`, `SchoolCodeService`).
- Produces:
  - `maskEmail(email: string): string`: `asha@school.in` → `a***@school.in`; one-character local part → `*@domain`.
  - `SchoolRegistrationService.register(input: SchoolRegistrationRequest): Promise<{ maskedEmail: string }>`. In one transaction (spec section 7): tenant `PENDING_VERIFICATION`, primary campus (via `withTenant`), user upsert by email, `OWNER` membership, token. Then enqueue the email. The raw token is 32 random bytes as base64url; the stored value is its SHA-256. Expiry is `REGISTRATION_TOKEN_TTL_HOURS`.
  - `SchoolRegistrationService.resend(input: { email: string; code: string }): Promise<void>`: no-op unless a matching pending tenant and owner exist. Marks earlier tokens used, issues a new one, and limits to 3/hour per email+code via Redis key `reg-resend:{email}:{code}` (`INCR` + `EXPIRE 3600`). Beyond the limit it throws `TooManyRequestsException`.
  - `SchoolRegistrationService.verify(token: string): Promise<{ code: string; name: string }>`: throws `GoneException` for unknown, used or expired tokens (one message: `This verification link is no longer valid.`).
  - Endpoints, with operationIds:
    - `POST /school-registrations` 202 (`createSchoolRegistration`)
    - `POST /school-registrations/resend` 202 (`resendSchoolRegistration`)
    - `POST /school-registrations/verify` 200 (`verifySchoolRegistration`)
  - `409` on a duplicate code (from the unique index or a pre-check), with `errors: [{ path: 'code', message: 'This school code is already taken.' }]` plus `suggestion` in the problem body.
