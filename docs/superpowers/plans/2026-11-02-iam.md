# IAM (Phase 1, Part 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Schools invite staff, give them roles built from a fixed permission catalogue, and the API and web app enforce those permissions, with required two-step per role, member management and an audit trail.

**Architecture:**

- **New `iam` module in the API.** It owns roles, role permissions, membership roles, invitations and audit events, all tenant-owned under forced RLS.
- **Permissions in the request pipeline.** Part 2a's session middleware also loads the member's roles and computes effective permissions on every request. A global `PermissionGuard` enforces `@RequirePermission` on top of that.
- **Joining.** Invitations reuse Part 2b's `completeFirstFactor` to sign a person in when they join.
- **Web app.** It gains a Users & roles area, a join page, a required-two-step setup page, and catalogue-based navigation.

**Tech Stack:** NestJS 11, Prisma 7, PostgreSQL 17 (RLS, SECURITY DEFINER), Redis, Next.js 16, next-intl, TanStack Query, shadcn/ui, Vitest, Testcontainers, Playwright + axe.

**Spec:** `docs/superpowers/specs/2026-11-02-iam-design.md` (section numbers refer to it). Base specs: Parts 1, 2a, 2b in the same folder.

## Global Constraints

- **Branch and commits:** branch `feat/p1-iam` from `main` after PR #9 merges. Use Conventional Commits with the harness's Co-Authored-By trailer. Open one PR against `main`.
- **RLS on every new table:** `roles`, `role_permissions`, `membership_roles`, `invitations` and `audit_events` are tenant-owned with forced RLS, and listed in `TENANT_SCOPED_MODELS`.
- **Append-only audit:** the app role has `INSERT, SELECT` on `audit_events` and nothing else.
- **Permission keys:** lowercase `module.action`, listed in spec §4 exactly. Actions are `view, create, edit, delete, export, approve, manage`.
- **Built-in roles** have these keys and defaults, as in spec §5:
  - `OWNER, PRINCIPAL, ADMIN, ACCOUNTANT, TEACHER, CLASS_TEACHER, LIBRARIAN, RECEPTIONIST, TRANSPORT_MANAGER`
  - `requires_two_factor` is true for OWNER, PRINCIPAL, ADMIN and ACCOUNTANT.
- **Owner role:**
  - It has no `role_permissions` rows; it means all permissions.
  - Only `requiresTwoFactor` is editable, and only by an owner.
  - It cannot be deleted.
- **Escalation:** a person may assign a role, or tick a permission, only within their own effective permissions. Only owners assign or remove the Owner role.
- **Last owner:** a school always keeps ≥ 1 active owner. A violation returns `409 last-owner`.
- **Invitations:**
  - 7-day expiry, single use.
  - Token: 32 random bytes, stored as SHA-256.
  - At most one open invitation per (school, email).
  - At most 3 resends per day per invitation.
  - At most 50 invitations per day per school.
- **IAM mutation limit:** 60 per hour per user.
- **Problem types:** `permission-denied`, `last-owner`, `already-member`, `already-invited`, `two-factor-setup-required`.
- **New enum values and columns:**
  - `MembershipStatus.DEACTIVATED`
  - `AuthMethod.INVITE`
  - `SessionRevokedReason.MEMBER_DEACTIVATED`
  - `sessions.two_factor_setup_required`
- **Removed:** `memberships.role` and the `MembershipRole` enum.
- **Pages:** `/[locale]/users-roles` (Members and Roles tabs), `/[locale]/users-roles/roles/[id]`, `/[locale]/users-roles/roles/new`, `/[locale]/join`, `/[locale]/setup-two-factor`.
- **Web quality bar:** all copy lives in `messages/en.json`. Axe must pass WCAG 2.1 AA in light and dark on the 6 device projects, with no overflow at 375 px. Touch targets are 44 px.
- **Local E2E:** run with `E2E_API_PORT=4100 E2E_WEB_PORT=3200` and a web build made with `API_INTERNAL_URL=http://localhost:4100`.

## Review Focus

1. **Stale permissions in an open tab.** After an admin removes a permission, the affected person's next API call gets `403`, and their next page load hides the menu item (Task 3 test, Task 11 E2E).
2. **Inviting someone who already has an account at another school.** One click joins, with no second account, and their existing password and two-step still apply (Task 6 test).
3. **Deactivated person still holding an open session.** Their very next request gets `401`, and sign-in then answers "incorrect" (Task 5 test).
4. **Admin tries to escalate through a custom role.** Creating or editing a role with a permission the admin lacks is refused, and so is cloning Owner as a non-owner (Task 4 test).
5. **Existing owners after the upgrade.** The owner is sent to two-step setup on their next request. After enabling it, everything works without signing in again (Task 7 test).
